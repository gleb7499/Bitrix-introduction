# AGENT.md — Общие инструкции для нейросети (правила при любом написании кода)

**Кратко:** этот файл содержит единые правила и паттерны, которым нужно строго следовать при создании фронтенд-кода для проекта: верстка по макету Figma и последующая интеграция в 1С-Битрикс. Документ включает общие принципы HTML/CSS/JS, паттерны из лабораторных работ (семантика, доступность, mobile-first, работа с DOM), а также специфичные инструкции по Bitrix.

---

## 1. Цель нейросети

1. Выдавать корректный, поддерживаемый и предсказуемый фронтенд-код, который можно быстро интегрировать в Bitrix-шаблон.  
2. Минимизировать риск конфликтов с legacy-кодом: явная изоляция стилей/скриптов, нейминг-контракты, минимальный побочный эффект.  
3. Всегда думать про доступность (a11y), адаптивность (mobile-first) и качество по метрикам (Lighthouse).

> 💡 **Личное напоминание (для разработчика):** ты будешь верстать сайт по макету из Figma, а затем вживлять его в Bitrix. Инструкции ниже отражают оптимальную стратегию для этого процесса.

---

## 2. Общий тон и подход при генерации кода

- Пиши короткие, понятные компоненты и файлы. Один файл — одна ответственность.  
- Отдавай предпочтение семантической разметке и читаемому, описательному неймингу классов (BEM-подобный или `project-component__elem--mod`), но всегда добавляй префикс шаблона, например `.pg-` или `.tpl-home-`.  
- Всегда соблюдай **mobile-first**: базовые стили — для мобильных, затем медиазапросы для планшетов/десктопов.  
- Пиши комментарии в коде, чтобы потом разработчик мог легко перенести написанную верстку в Bitrix.  
- **Безопасность:** не вставляй чувствительные данные (пароли, API-ключи), не используй `eval()` и не генерируй HTML из ненадёжных строк без очистки.  

---

## 3. Правила HTML — семантика и доступность

1. Используй **HTML5 landmarks**: `header`, `nav`, `main`, `aside`, `section`, `article`, `footer`.  
2. Правильная иерархия заголовков: `h1` — на странице один (или логично распределённые), далее `h2`, `h3`.  
3. Картинки — всегда с `alt`. Декоративные — `alt=""` и `aria-hidden="true"`, значимые — информативный текст.  
4. Обеспечивай видимый фокус (`outline`) для интерактивных элементов; не убирай `:focus` без альтернативы.  
5. Формы: `label` для полей, `aria-describedby` для подсказок/ошибок, используем семантические типы (`email`, `tel`), реальная клиентская валидация.  
6. **ARIA:** применяй только при необходимости, следуй рекомендациям (`role="dialog"`, `aria-modal="true"`, `aria-expanded` для аккордеонов).  
7. **Тесты a11y:** ориентируйся на Lighthouse Accessibility и ручные проверки клавиатурой (`Tab`, `Shift+Tab`, `Enter`, `Esc`).

## 4. CSS-паттерны и структура

**Основные правила:**

- Файловая структура:  
  
   ```text
   assets/css/reset.css
   assets/css/base.css
   assets/css/components/*.css
   assets/css/layout/*.css
   assets/css/pages/*.css
   ```

- Именование: префикс шаблона (`tpl-` / `pg-`) + компонентный нейминг. Примеры: `.pg-hero`, `.pg-nav__item`.  
- **Scoping:** каждый крупный блок страницы оборачивать в контейнер, например `<main class="page-home">`, и писать селекторы внутри этого скоупа — это снижает конфликты с legacy.  
- **Mobile-first:** писать базовые стили для мобильной ширины, затем  
  
   ```css
   @media (min-width: 601px) { ... }
   @media (min-width: 1025px) { ... }
   ```

Минимум 2 брейкпоинта: `≤600px`, `601–1024px`, `>1024px`.

- **Layout:** предпочитать Flexbox и CSS Grid для построения сеток; использовать `gap` вместо margin-хаков.
- **Performance:** минимизировать количество критических CSS. Критические стили можно вынести в `<head>` (строго минимально), остальное — в отдельный файл.
- **Ресурсы:** использовать `<picture>` + `srcset` для адаптивных изображений.

**Кодстайл:**

- Отступы: 2 пробела.
- Переменные CSS (если используются) — `--pg-primary-color`.
- Комментарии для сложных частей.

## 5. JavaScript-паттерны

**Общие принципы:**

- Чистый **ES6+** код, модули (`type="module"`) — если проект позволяет.
- Не использовать jQuery; манипуляции через `document.querySelector` / `addEventListener`.
- Избегать глобальных переменных — всё помещать в IIFE или модули.
- Делегирование событий: в списках и множественных интеракциях назначать обработчики на контейнер.
- **A11y поведение:** при открытии модальных окон переводить фокус внутрь, возвращать фокус после закрытия; управлять `aria-expanded` / `aria-hidden`.
- **Формы:** валидация при вводе и при сабмите; кнопка отправки `disabled`, если форма невалидна; не делать реального запроса — имитировать (или отправлять через API, если есть спецификация).
- **Сохранение состояния (опционально):** `localStorage` для состояния UI (например, открытые табы).

**Примеры обязанностей кода:**

- Аккордеон: кнопки с `aria-expanded`, панели с `aria-hidden` и `id` для `aria-controls`.
- Модалки: `role="dialog"`, `aria-modal="true"`, обработка `Esc`, **focus trap** (или облегчённая версия).
- Делегирование:

  ```js
  listContainer.addEventListener('click', (e) => {
    const btn = e.target.closest('.card__remove');
    if (!btn) return;
    // логика удаления
  });
  ```

## 6. Критерии качества (чек-лист перед сдачей)

- Семантика: использованы `header/nav/main/section/article/footer` и корректная иерархия заголовков.
- Адаптивность: **mobile-first** + минимум 2 брейкпоинта; проверка на 360px / 768px / 1366px.
- Доступность: `alt`, `label`, видимый фокус, управление клавиатурой, `aria-атрибуты`.
- **Lighthouse:** Accessibility & Best Practices ≥ 90 (или максимально близко), нет критических ошибок.
- **Валидность:** HTML/CSS без ошибок валидатора.
- **Совместимость:** не ломает существующие компоненты Bitrix; использование `local/templates`.
- **Производительность:** изображения адаптивные, минимально критический CSS, не блокирующие скрипты.

## 7. Инструменты для проверки и дебага

- Browser DevTools — responsive mode, Lighthouse.
- HTML/CSS валидаторы: [validator.w3.org](https://validator.w3.org/), [CSS validator](https://jigsaw.w3.org/css-validator/).
- Линтеры: ESLint (JS), stylelint (CSS) — по возможности.

---

## 8. Частые ошибки и как их избегать

- Глобальные селекторы — избегать `body h1` и подобных, лучше использовать scoped классы.
- Игнорирование a11y — всегда думать про клавиатуру и aria.
- Встраивание бизнес-логики в верстку — логика должна быть в компонентах/модулях Bitrix, верстка — только представление.

---

## 9. Заключение — мудрые правила для нейросети

1. **Семантика и доступность важнее «красивого» DOM трюка.**
   Всегда выбирай читабельность и понятность структуры над изощрёнными визуальными решениями. Семантика — это не украшение, а прочный каркас интерфейса.

2. **Mobile first + scoped styles = минимальная вероятность поломать legacy.**
   Верстай для мобильных, расширяй для больших экранов. Всегда ограничивай область действия стилей, чтобы не затронуть старые части Bitrix.

3. **Чистота и изоляция.**
   Любой кусок верстки должен быть переиспользуемым, без скрытых зависимостей. Каждый блок — самодостаточный и независимый.

4. **Доступность — это часть качества.**
   Управление с клавиатуры, правильные ARIA атрибуты, видимый фокус и контраст не обсуждаются. Интерфейс, недоступный хотя бы одной группе пользователей — неполноценен.

5. **Код должен объяснять себя сам.**
   Пиши так, чтобы другой разработчик понял твой код без комментариев. Комментарии нужны лишь там, где логика вынужденно сложна.

6. **Минимум зависимости от окружения.**
   Не опирайся на случайные классы Bitrix или старые таблицы. Всё новое должно быть автономным.

7. **Лёгкость интеграции важнее “магии”.**
   Простая, чистая структура HTML/CSS/JS ускоряет внедрение в CMS и снижает риск конфликтов с legacy.

8. **Ошибки неизбежны, но важна предсказуемость.**
   Если что-то пойдёт не так, код должен вести себя стабильно: без поломки страницы.

9. **Проверяй всё руками.**
   Даже при автотестах — смотри глазами: адаптив, отступы, поведение клавиатуры. Верстка — это ремесло.

10. **Не гонись за “идеальной” версией — гонись за надёжной.**
    Лучшая верстка — та, что выдерживает адаптив, кеш и три релиза подряд.

11. **Помни: нейросеть — твой помощник, не художник.**
    Она должна думать как инженер Bitrix, а не как креативный дизайнер.
    Если не уверен — выбери **семантику, чистоту и надёжность**. Всё остальное можно доделать потом.
12. **Придерживайся уже созданной структуры проекта.**
    Не вноси радикальных изменений в организацию файлов и стилей без веской причины. Стабильность важнее экспериментов.
